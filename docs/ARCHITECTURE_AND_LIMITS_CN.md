# 当前不足与后续优化路线

本文记录这个 Demo 当前能做什么、主要限制在哪里，以及建议按什么顺序改进。实测数据来自特定 RK3588 板、Linux 6.1.141、双 IMX415、对应驱动/IQ 和当前模型；它们是工程实测值，不是所有 RK3588 板都能保证的指标。

## 当前能力与边界

| 项目 | 当前状态 | 直接影响 |
|---|---|---|
| 全局摄像头 | CSI3 以 3840×2160 RAW10、约 60 FPS 采集；ISP 输出 960×540 NV12 后送 YOLOv5n | 4K 输入在 ISP 后缩小到 960×540，小而远的人体细节会丢失，检测能力受模型输入尺寸限制 |
| 高速 ROI 摄像头 | CSI4 传感器直接读出 648×640 RAW10，有效 ROI 为 640×640，约 109–111 FPS；ISP 输出 640×480 NV12 | 这是 Sensor 端 ROI；不是从 4K ISP 图像软件裁剪。640×480 ISP 输出还会改变视野/纵横比例 |
| 推理调度 | 三个 NPU 核使用独立 worker；空闲时并行处理全局帧，发现目标后将更多 NPU 时间分给 ROI | ROI 优先时全局刷新率会下降；当前是吞吐优先策略，不是全局与 ROI 帧率均有硬保证的实时调度 |
| 目标到 ROI 映射 | 通过全局框中心、归一化坐标、scale/offset 推算 CSI4 ROI 起点 | 两摄像头未做精确标定；基线、视差、安装角和目标距离都会造成偏移 |
| 输入与显示格式 | V4L2 输出 NV12；C++ 推理路径使用 RGA/imageutils 做预处理；Python/OpenCV 负责 HDMI 合成 | 仍有 CPU 内存复制、颜色转换、缩放和画面合成成本，端到端路径不是零拷贝 |
| 运行拓扑 | 当前脚本固定 CSI3 `/dev/media4`、`/dev/v4l-subdev2`、`/dev/video44`，CSI4 `/dev/media5`、`/dev/v4l-subdev7`、`/dev/video53` | 换板、换 DTB 或设备探测顺序后节点可能变化，硬编码可能打开错误摄像头或启动失败 |
| 摄像头图像质量 | ROI IQ 已补充 `640x640` LSC 条目，解决过 RAW 正常但 ISP NV12 全黑 | IQ 针对当前模组和模式；ROI 全视场的 shading、暗光噪声和色彩一致性仍需专门标定 |
| 性能验证 | 已有约 15 秒级运行记录和若干 FPS 观测；主 README 记录空闲全局约 59–60 FPS、ROI 输入约 109–111 FPS、ROI 推理约 97–101 FPS | 缺少统一脚本、长时间热稳定数据、端到端时延分布、丢帧率、功耗和正式检测精度报告 |

### 性能数据的口径

摄像头采集 FPS、NPU 推理 FPS、显示 FPS 是不同指标，不能互相替代。历史测试中的 ROI 推理吞吐有约 90–92、97–101、100–106.5 FPS 等记录，测试时长、运行模式和统计口径不同；目前应将约 97–101 FPS 视为参考观测值，不视为统一验收保证。

另一个容易踩坑的点是全局检测周期：C++ 程序直接运行时默认 `--global-period-ms 500`，而部署脚本 `runtime/run.sh` 默认传入 `GLOBAL_PERIOD_MS=100`。两种启动方式下 ROI 激活时的全局刷新率差异明显。简历或报告引用帧率时，应同时写明提交版本、启动脚本、周期参数、测试时长和统计日志。

## 需要优先处理的问题

### P0：正确性、可移植性与可复现性

1. **设备节点写死。** `imx415-dual-person-demo.cc` 和 `configure-cameras.sh` 固定了 video、subdev、media 编号。应按 media entity 名称和传感器 I²C 地址自动发现拓扑，并通过配置文件或命令行传给程序。验收：同一软件包在节点编号不同的两块板上能自动找到两路摄像头，并能明确报告映射结果。
2. **启动参数有两套默认值。** 二进制默认全局周期为 500 ms，`run.sh` 默认 100 ms。应只保留一个配置来源，并把实际启动参数写入日志。验收：从脚本和直接运行获得相同默认行为，日志可复现每次性能测试。
3. **共享检测状态存在同步隐患。** worker 在线程锁内更新 person 状态，但主线程输出周期日志时有字段在锁外读取。应将检测框、是否检测到人、置信度和帧序号一起复制为一个受锁保护的快照，或改用明确的原子结构。验收：启用 ThreadSanitizer 的主机测试无数据竞争报告，板端长时间运行无状态错配。
4. **AIQ 服务管理影响范围过大。** 相机配置脚本直接结束并重启 `rkaiq_3A_server`，可能影响同板的其他相机业务。应采用明确的服务单元、互斥检查和失败回滚。验收：启动/停止本 Demo 不会中断未参与 Demo 的相机服务。
5. **驱动、DTB、IQ、运行库版本耦合。** 用户态包不能单独带来高速 Sensor ROI；boot 镜像也只是特定板型的 boot 分区镜像。应维护版本清单、构建来源、板型检查和回滚步骤。验收：部署前检查板型和版本，不匹配时停止而不是继续覆盖。

### P1：提升跨相机 ROI 命中率

1. 使用棋盘格或已知标志点做两相机标定，先测不同图像位置和距离下的映射误差。固定平面场景可评估单应矩阵；目标距离明显变化时不能只靠单一平面映射，应增加深度假设或扩大 ROI 安全边界。
2. 当前主目标按 person 置信度选择，没有稳定的跨帧 ID 关联。增加轻量跟踪器或 Kalman 状态预测，根据目标速度预判 ROI 位置；加上移动死区、最大移动速度、滞回和目标丢失后的扩大/搜索策略。
3. 多人时定义明确的主目标策略，例如保持已有 ID、按业务优先级、目标面积或离画面中心距离排序；检测结果应带帧序号和时间戳，避免旧结果覆盖新结果。

验收指标建议：在近/中/远距离、画面中心与边缘、横向/纵向快速运动、多人和短暂遮挡下统计“目标完整落入 ROI 的帧比例”、ROI 重定位延迟、误切换次数和恢复时间。

### P2：降低 CPU 与内存带宽

1. `LatestCamera` 从 V4L2 MMAP 帧复制到新建的 `vector`；预览输出再 `memcpy` 到共享内存。改成固定缓冲池、DMABUF 导入和引用计数，减少逐帧分配与复制。跨 V4L2/RGA/RKNN 使用外部内存时，需验证缓存一致性和 buffer 生命周期。
2. HDMI 显示程序将 NV12 复制成 NumPy 数据，再用 OpenCV 做 NV12→BGR、缩放、画框和 1920×1080 合成。可以改为 RGA 合成加 DRM/KMS overlay/plane，或使用有硬件路径的 GStreamer，减少 CPU 图像处理。
3. 固定预分配中间 buffer，限制日志频率；增加每阶段耗时和 CPU 占用统计。只有在测得内存复制确为瓶颈后，再推进更复杂的零拷贝路径。

验收指标建议：同一场景记录 CPU 总占用、内存带宽、采集到显示的 P50/P95 延迟、NPU 推理吞吐和丢帧率；比较优化前后数据，确保不是仅让显示 FPS 变高而推理时延变差。

### P3：改善检测精度和画质

1. 用目标摄像头、实际安装高度、距离、室内外和照明条件采集代表性数据，统计 person 的 precision/recall、漏检和误检；不能用单张 COCO 图片验证代替现场精度评测。
2. 针对部署数据重新做 INT8 量化校准或微调模型，重点评估远距离小目标、遮挡、逆光、运动模糊和夜间噪声。若全局 960×540 降采样是主要漏检原因，再评估提高全局 ISP 输出尺寸或采用低成本候选检测方案，并量测增加的 DDR/NPU 负载。
3. 重新标定 ROI 模式下的 LSC、黑电平、降噪、曝光和色彩参数。110 FPS 帧周期约 9 ms，暗光下可用曝光时间短，增益升高后噪声会增加；可评估 60/90/110 FPS 档位随光照或任务状态切换。

验收指标建议：在固定测试集上报告 precision/recall 或 mAP、按目标尺寸分桶的召回率，并同时报告曝光、增益、帧率和端到端延迟。

### P4：形成可交付的工程验证

1. 记录准确的 kernel/DTB、驱动、IQ、RKNN runtime、RGA、模型和应用版本及 SHA-256；固定编译工具链和 `rknn_model_zoo` 基线，补充可复现构建脚本。
2. 增加坐标映射、边界裁剪、偶数对齐、NV12 stride/尺寸和 selection 失败路径的自动化测试；增加用户态异常退出后的清理与重启测试。
3. 建立 10 分钟双路并发冒烟测试和 30 分钟以上热稳定测试，采集 kernel 的 CRC/ECC/overflow/size 错误、温度/降频、CPU/NPU/DDR 使用率和功耗。
4. 用统一 JSONL 或 CSV 记录每帧采集时间、推理开始/结束、结果帧号、ROI 移动时间和显示时间，计算端到端 P50/P95/P99 延迟、有效推理帧率和丢帧比例。

## 优化顺序建议

```text
先让启动参数和测试口径一致
  → 自动发现摄像头拓扑并修复线程快照
  → 完成跨摄像头标定与 ROI 预测
  → 减少帧复制并优化 HDMI 硬件合成
  → 用现场数据优化模型/IQ，再进行长时间热稳定验收
```

不建议一开始同时改传感器时序、ISP、NPU 调度和模型。每次只改变一个主变量，并保留原有镜像、IQ、程序和测试日志作为对照。

## 性能声明边界

- 当前已稳定验证的高速 ROI 采集参考值约 110 FPS；此前 166 FPS 来自另一套 ROI 寄存器/时序组合，不能据此宣称当前包可达到 166 FPS。
- 达到更高 Sensor 帧率仍需同时验证 VMAX/HMAX、曝光上限、MIPI lane 时钟、blanking、接收 PHY、CIF/ISP 带宽和长时间错误计数；改应用线程不能突破传感器或链路上限。
- 当前 CSI3/CSI4 是固定部署配置。迁移前要核对 media graph、Sensor I²C 地址、subdev/video 节点、IQ 模组和驱动版本。
